1. Arquitectura General y Flujo de Datos

La aplicación implementa el patrón MVC (Modelo - Vista - Controlador) asistido por el patrón DAO (Data Access Object). Los componentes se dividen claramente las responsabilidades:

Navegador (Cliente)
 → 
Servlet (Controlador)
 → 
DAO (Persistencia)
 → 
Oracle DB

HTML generado
 ← 
Vistas JSP
 ← 
request.setAttribute(...)
 ← 
Objetos Modelo
  • Modelo (model): Clases POJO/JavaBeans (Producto, Alojamiento, Marca, Categoria). Solo guardan datos con getters/setters.
  • Vista (views/*.jsp): Ubicadas dentro de WEB-INF/ para impedir acceso directo por URL. Usan JSTL y Expression Language (EL).
  • Controlador (Servlet): Único punto de entrada para peticiones web. Interpreta el parámetro accion, pide datos al DAO y despacha la vista.
  • Persistencia (DAO): La única clase autorizada a escribir código SQL JDBC. Convierte registros de tablas a objetos Java.

2. Configuración y Descriptor de Despliegue

  • pom.xml (Maven): Gestiona jakarta.servlet-api (scope provided, pues lo aporta Tomcat 10.1+), jakarta.servlet.jsp.jstl (para etiquetas en JSP) y ojdbc11 (driver JDBC para base de datos Oracle).
  • web.xml: Contiene <welcome-file>alojamientos</welcome-file> (o productos). Si el usuario accede a la raíz de la web, el servidor lo redirige automáticamente a la URL del Servlet.

3. Conexión a Base de Datos (ConnectionFactory)

Clase estática (patrón Factory) con constructor privado para evitar instanciación:

public final class ConnectionFactory {
    private static final String URL = "jdbc:oracle:thin:@80.28.158.14:1521:oradai";
    private static final String USER = "...";
    private static final String PASSWORD = "...";

    static {
        try {
            Class.forName("oracle.jdbc.OracleDriver"); // Carga estática del driver JDBC
        } catch (ClassNotFoundException e) {
            throw new ExceptionInInitializerError("Driver Oracle no encontrado");
        }
    }

    public static Connection getConnection() throws SQLException {
        return DriverManager.getConnection(URL, USER, PASSWORD);
    }
}

4. Clases de Dominio (El Modelo)

Siguen la convención JavaBean: atributos privados, constructor por defecto y getters/setters públicos.

Pregunta Clave: ¿Por qué BigDecimal para precios?
Los tipos primitivos double y float sufren imprecisión de coma flotante binaria (p. ej. 0.1 + 0.2 = 0.30000000000000004). En aplicaciones comerciales y financieras se usa BigDecimal para garantizar precisión matemática decimal exacta.
Relaciones entre Objetos: En las clases de modelo no se guardan simples int para las claves foráneas, sino objetos completos (private Localidad localidad; private Tipo tipo;). Esto permite navegar por las relaciones en JSP de forma limpia: ${alojamiento.localidad.nombre}.

5. Capa DAO (Data Access Object)

Encapsula todas las operaciones contra Oracle. Utiliza try-with-resources para cerrar automáticamente conexiones, sentencias y resultados.

Método Sentencia SQL Puntos Técnicos Clave
findAll() SELECT ... JOIN ... JOIN ... Usa alias (e.id AS entity_id, r1.id AS localidad_id) para evitar colisiones de columnas idénticas. Mapea cada fila con método privado de mapeo.
findById(int) SELECT ... WHERE e.id = ? Usa PreparedStatement con ? (previene SQL Injection). Devuelve Optional<T> para controlar elegantemente si el registro no existe.
insert(T) INSERT INTO tabla (campos...) VALUES (?, ...) NO incluye el ID si es autonumérico (generado por secuencia/trigger de Oracle). Usa ps.executeUpdate().
update(T) UPDATE tabla SET campo1=?, campo2=? ... WHERE id=? La palabra SET solo se escribe una vez separada por comas. El id se pasa al final en el WHERE id = ?.
delete(int) DELETE FROM tabla WHERE id = ? Elimina por clave primaria mediante PreparedStatement.

6. El Servlet (El Controlador)

Anotado con @WebServlet("/alojamientos") (o /productos). Su método init() instancia los DAOs una única vez al arrancar.

A. Método doGet (Peticiones de Lectura / Navegación)

Interpreta request.getParameter("accion") (por defecto "listar"):

  • listar → Consulta dao.findAll(), asigna request.setAttribute("items", ...) y hace forward(..., "listado.jsp").
  • detalle → Valida id con requiredInt(). Si no existe, devuelve response.sendError(404). Si existe, lo publica y hace forward a detalle.jsp.
  • nuevo → Consulta las tablas relacionadas para los desplegables, define request.setAttribute("modo", "crear") y abre formulario.jsp.
  • editar → Carga el registro por ID, publica las tablas relacionadas, define request.setAttribute("modo", "actualizar") y abre formulario.jsp.

B. Método doPost (Modificaciones en Base de Datos)

Empieza con request.setCharacterEncoding("UTF-8") para respetar caracteres especiales. Ejecuta:

  • crear → Lee el formulario con readForm(request), llama a dao.insert(item) y aplica Post/Redirect/Get.
  • actualizar → Lee el ID oculto (int id = requiredInt(request, "id")), lee los demás campos con readForm(), asigna item.setId(id) y llama a dao.update(item).
  • eliminar → Lee id por POST, llama a dao.delete(id) y redirige. Nunca se elimina por GET.
El Patrón Post / Redirect / Get (PRG):
Tras un INSERT, UPDATE o DELETE por POST, nunca se hace forward. Siempre se hace response.sendRedirect(request.getContextPath() + "/alojamientos").
Razón: Si hiciéramos forward, la última petición del navegador seguiría siendo POST. Si el usuario pulsa F5 (recargar), el navegador reenviaría el formulario y duplicaría los registros en la base de datos.

7. Capa de Vista: Vistas JSP

Las JSPs residen en /WEB-INF/views/ por motivos de seguridad: un cliente externo no puede invocarlas directamente en el navegador, forzando a que todas las peticiones pasen por el Servlet.

Reglas de Expresión (EL - Expression Language)

  • ${item.nombre} → Invoca automáticamente item.getNombre().
  • ${item.localidad.nombre} → Invoca item.getLocalidad().getNombre().
  • Operador Ternario: ${condicion ? valor_si_true : valor_si_false}.
    Ejemplo: ${alojamiento.destacado ? 'Destacado' : 'Estándar'}.

Formulario Dual (formulario.jsp)

Un único formulario cubre tanto la Creación como la Edición:

<form action="${pageContext.request.contextPath}/alojamientos" method="POST">
    <%-- Acción dinámica: "crear" o "actualizar" según la variable enviada por el Servlet --%>
    <input type="hidden" name="accion" value="${modo}">
    
    <%-- ID oculto: viaja vacío en altas, con número en edición --%>
    <input type="hidden" name="id" value="${alojamiento.id}">

    <input type="text" name="nombre" value="${alojamiento.nombre}">
    <input type="number" name="precioNoche" value="${alojamiento.precioNoche}" step="0.01">

    <%-- Desplegable con preselección automática al editar --%>
    <select name="localidadId">
        <c:forEach var="loc" items="${localidades}">
            <option value="${loc.id}" ${alojamiento.localidad.id == loc.id ? 'selected' : ''}>
                ${loc.nombre}
            </option>
        </c:forEach>
    </select>
</form>

8. Banco Completo de Preguntas de Examen (Con Respuestas)

1. ¿Por qué el botón "Eliminar" se implementa con un <form method="POST"> y nunca con un enlace <a href="...">?
Respuesta: Porque según el protocolo HTTP, las peticiones GET deben ser seguras e idempotentes (solo lectura). Los enlaces <a href> son GET; si eliminar fuera un enlace, un rastreador web (como el bot de Google), una previsualización de enlace en un navegador o un usuario compartiendo la URL podría destruir registros en la base de datos sin confirmación. Toda alteración en el servidor debe viajar por POST.
Pista de código: En detalle.jsp usamos <form method="POST" action="..."> con <input type="hidden" name="accion" value="eliminar"> y <input type="hidden" name="id" value="${alojamiento.id}">.
2. ¿Qué es el patrón Post/Redirect/Get (PRG) y qué problema exacto resuelve en crear(), actualizar() y eliminar()?
Respuesta: Resuelve el problema del doble envío o duplicidad de datos al pulsar F5.
Si tras un POST hiciéramos un forward a la vista del listado, la última petición del navegador seguiría siendo POST. Si el usuario recarga la página (F5), el navegador muestra la alerta "¿Desea volver a reenviar el formulario?" y duplicaría la inserción o actualización.
Con PRG, tras procesar el POST en el servidor respondemos con response.sendRedirect(request.getContextPath() + "/alojamientos") (código HTTP 302). Esto obliga al navegador a realizar una nueva petición GET limpia. Si ahora el usuario pulsa F5, solo refresca el listado.
3. ¿Qué diferencia hay entre forward y sendRedirect? ¿Cuándo se usa cada uno?
forward (RequestDispatcher): Se produce íntegramente dentro del servidor. La URL del navegador no cambia y la petición se mantiene (conservando los atributos de request.setAttribute). Se utiliza en operaciones de lectura (GET) para transferir los datos del Servlet a la JSP.
sendRedirect (HttpServletResponse): El servidor envía una respuesta HTTP 302 al navegador con una cabecera Location. El navegador realiza una segunda petición HTTP GET independiente a esa nueva URL. Se usa tras operaciones de escritura (POST) dentro del patrón PRG.
4. ¿Por qué en el método actualizar() es imprescindible hacer alojamiento.setId(id) a mano?
Respuesta: Porque el método auxiliar readForm(request) lee y valida los campos que el usuario teclea en el formulario (nombre, precio, capacidad, etc.), pero no lee el ID. Si no extraemos el ID del campo oculto (int id = requiredInt(request, "id")) y hacemos alojamiento.setId(id), el objeto mantiene su id = 0 por defecto. Al llamar al DAO se ejecutaría WHERE ID = 0, por lo que no actualizaría ninguna fila en Oracle sin dar error visible.
5. ¿Cómo se gestionan las dos relaciones foráneas (Localidad y Tipo) en el Modelo, en el Formulario y en el DAO?
En el Modelo (Alojamiento.java): Seguimos el paradigma de objetos: en lugar de simples enteros (localidadId), guardamos referencias a objetos completos (private Localidad localidad; private Tipo tipo;). Esto permite acceder en JSP a ${alojamiento.localidad.nombre}.
En el Formulario (formulario.jsp): Se crean dos <select> cuyos name son localidadId y tipoId. Se recorren las colecciones con <c:forEach> y se preselecciona la opción actual mediante el operador ternario: ${alojamiento.localidad.id == loc.id ? 'selected' : ''}.
En el Servlet (readForm): Se leen los IDs con requiredInt(), se buscan los objetos en LocalidadDAO y TipoDAO, y se inyectan en el alojamiento.
En el DAO (AlojamientoDAO): Las consultas SELECT usan JOIN con alias (r1.id AS localidad_id, r2.id AS tipo_id) para evitar colisiones de columnas con el mismo nombre.
6. ¿Por qué las vistas JSP se colocan dentro de /WEB-INF/views/ y no en la raíz web pública?
Respuesta: Por seguridad y control de acceso. La especificación Java EE/Jakarta EE prohíbe que el servidor sirva directamente cualquier archivo que esté bajo la carpeta /WEB-INF/ ante una petición directa desde el navegador (si un usuario teclea /WEB-INF/views/detalle.jsp recibirá un error 404).
Esto fuerza a que el usuario tenga que pasar obligatoriamente por el AlojamientoServlet, garantizando que los datos se lean primero de la base de datos y se inyecten con request.setAttribute.
7. ¿Qué diferencia hay entre request.getParameter() y request.getAttribute()?
request.getParameter("nombre"): Recupera valores en formato String enviados por el cliente / navegador (bien por la URL en un GET, o en el cuerpo del formulario en un POST). Solo es de lectura.
request.getAttribute("nombre"): Recupera objetos Java arbitrarios (Listas, Objetos del Modelo) que hemos depositado nosotros mismos en el servidor mediante request.setAttribute("nombre", objeto) para comunicarnos con la JSP.
8. ¿Por qué usamos PreparedStatement en lugar de Statement simple?
1. Seguridad frente a Inyección SQL: Los parámetros marcados con ? son tipados y tratados estrictamente como datos, nunca como código ejecutable por el motor de base de datos.
2. Rendimiento: La base de datos compila y optimiza el plan de ejecución de la consulta la primera vez; si se ejecuta varias veces (por ejemplo en un bucle), reutiliza la consulta precompilada cambiando solo los parámetros.
9. ¿Por qué usamos BigDecimal para el precio por noche y no double o float?
Respuesta: Los tipos primitivos float y double utilizan representación binaria en coma flotante según el estándar IEEE 754, lo que provoca imprecisiones de redondeo (por ejemplo 0.1 + 0.2 = 0.30000000000000004). En aplicaciones financieras, contables y de reservas se exige exactitud decimal absoluta, por lo que siempre se debe emplear BigDecimal.
10. ¿Cómo se procesa un campo booleano como un checkbox (destacado) en el formulario y en el Servlet?
En HTML: Si el checkbox está marcado, el navegador envía el parámetro en la petición; si el usuario no lo marca, el navegador no envía absolutamente nada (el parámetro viaja como null).
En Java (readForm): Se comprueba si el parámetro existe o no:
alojamiento.setDestacado(request.getParameter("destacado") != null);
Si no es nulo, vale true; si es nulo, vale false.
11. ¿Cómo maneja el proyecto los casos de error: ID inexistente o ID no numérico?
ID no numérico (p. ej. /alojamientos?accion=detalle&id=abc): El método requiredInt() intenta hacer Integer.parseInt(), el cual lanza NumberFormatException (subclase de IllegalArgumentException). El bloque try-catch principal del Servlet la captura y devuelve un error HTTP 500 controlado o mensaje de error sin romper el servidor.
ID inexistente (p. ej. id=9999): alojamientoDAO.findById(9999) devuelve Optional.empty(). El Servlet evalúa if (alojamiento == null) y ejecuta response.sendError(404, "Alojamiento no encontrado").
12. ¿Por qué usamos try-with-resources en todos los métodos del DAO?
Respuesta: Todo objeto que implementa la interfaz AutoCloseable (como Connection, PreparedStatement y ResultSet) colocado dentro del paréntesis de try (...) se cierra automáticamente al finalizar el bloque, incluso si ocurre una excepción.
Esto previene la saturación del pool de conexiones de Oracle (fugas de cursores y conexiones huérfanas en el servidor).
